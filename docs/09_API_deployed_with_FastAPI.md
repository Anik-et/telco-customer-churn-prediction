# 09 - API Deployment with FastAPI

## 1. Objective

The objective of this stage is to expose the trained churn prediction pipeline through a web API.

Until now, predictions have been generated by calling the Python prediction pipeline directly.

The next step is to allow another application to send customer information over HTTP and receive a prediction.

The target architecture is:

    Client / Application
            |
            v
        HTTP Request
            |
            v
        FastAPI API
            |
            v
      PredictPipeline
            |
            v
       Preprocessor
            |
            v
       XGBoost Model
            |
            v
       Prediction
            |
            v
        JSON Response

The API therefore acts as the interface between the machine learning model and other applications.

---

# 2. Why Build an API?

A trained model sitting inside a Python script is not easily consumable by other applications.

For example, a business application may need to ask:

> What is the churn risk for this customer?

An API allows the application to send the customer data to the ML service and receive a structured response.

This creates a separation between:

    Client Application

and:

    Machine Learning Service

The client does not need to know how the model works internally.

---

# 3. What is FastAPI?

FastAPI is a Python framework for building APIs.

It is particularly useful for machine learning inference services because it supports:

- HTTP endpoints
- JSON request/response handling
- Input validation
- Automatic API documentation
- Python type hints
- Asynchronous programming when needed

For this project, FastAPI provides the web layer around the existing `PredictPipeline`.

---

# 4. API vs Prediction Pipeline

These two components have different responsibilities.

## PredictPipeline

Responsible for:

- Loading the model
- Loading the preprocessor
- Transforming input
- Generating predictions
- Calculating probability
- Assigning risk level

## FastAPI

Responsible for:

- Receiving HTTP requests
- Validating request structure
- Calling `PredictPipeline`
- Returning a JSON response
- Handling API-level errors

Conceptually:

    FastAPI
       |
       v
    PredictPipeline
       |
       v
    ML Model

Keeping these responsibilities separate makes the application easier to maintain.

# 9. Pydantic Request Models

FastAPI commonly uses Pydantic models to define request schemas.

Conceptually:

    class CustomerRequest(BaseModel):
        gender: str
        SeniorCitizen: int
        Partner: str
        Dependents: str
        tenure: int
        ...

The schema describes:

- Which fields are required
- What type each field should have
- How incoming JSON should be parsed

This provides an explicit API contract.

---

# 10. Why Input Validation Matters

Without validation, invalid input may reach the model.

Examples:

    tenure = "abc"

or:

    MonthlyCharges = "unknown"

or:

    SeniorCitizen = 100

These values may cause errors or produce meaningless predictions.

API validation provides an early protection layer.

The flow becomes:

    Invalid Request
          |
          v
    Validation
          |
          v
    Reject Request

rather than:

    Invalid Request
          |
          v
    Model
          |
          v
    Unexpected Behavior

---

# 11. Schema Validation vs Model Validation

API validation should not replace the model's data transformation logic.

They serve different purposes.

## API validation

Checks:

- Request structure
- Required fields
- Basic data types
- Basic constraints

## Data transformation

Checks/processes:

- Numeric conversion
- Missing values
- Feature transformation
- Encoding
- Scaling

## Model

Performs:

- Prediction

Therefore:

    API Validation
          |
          v
    Data Transformation
          |
          v
    Preprocessing
          |
          v
    Model

# 40. Model Loading and Memory

Loading a model once per service instance is usually preferable to loading it for every request.

Instead of:

    Request
       |
       v
    Load model
       |
       v
    Predict
       |
       v
    Unload

prefer:

    Service Start
       |
       v
    Load model
       |
       v
    Keep model in memory
       |
       +--> Request 1 -> Predict
       +--> Request 2 -> Predict
       +--> Request 3 -> Predict

This reduces repeated disk I/O and model initialization overhead.

# 43. Sensitive Customer Data

The churn dataset contains customer-related information.

A production API should minimize exposure of customer data.

Important practices include:

- Do not log complete customer requests unnecessarily.
- Restrict API access.
- Encrypt data in transit.
- Protect stored logs.
- Apply appropriate data-retention policies.
- Follow organizational privacy requirements.

The model service should only receive the information required for prediction.

# 50. API Versioning

Suppose the first API accepts:

    /api/v1/predict

Later, the request schema changes.

    /api/v2/predict

# 52. Timeout Handling

The API should have sensible timeout behavior.

A request should not remain active indefinitely.

Timeouts can protect the service from:

- Slow dependencies
- Resource exhaustion
- Network problems
- Unexpected processing delays

For this lightweight tabular model, inference is expected to be relatively fast, but timeout handling remains a production concern.

# 68. Common Interview Question: Why FastAPI?

Answer:

> "FastAPI provides a lightweight way to expose Python inference logic through HTTP. It has strong request validation through Pydantic, automatic API documentation and good performance. More importantly, it lets me keep the API layer separate from the ML prediction pipeline."

# 69. Common Interview Question: Why Load the Model Once?

Answer:

> "Loading the model from disk for every request adds unnecessary latency and disk I/O. I would load the model and preprocessor when the service starts and reuse them for subsequent inference requests. Each service instance maintains its loaded model in memory."

---

# 70. Common Interview Question: How Do You Prevent Training-Serving Skew?

Answer:

> "I reuse the exact fitted preprocessing pipeline from training during inference. I do not fit a new preprocessor on incoming customer data. This ensures that imputation, scaling, encoding and feature ordering remain consistent."

---

# 71. Common Interview Question: How Do You Handle Unknown Categories?

Answer:

> "The categorical encoder uses `handle_unknown='ignore'`, so an unseen category does not cause inference to fail. In production I would additionally monitor the frequency of unseen categories because a sudden increase could indicate data drift or a schema change."

# 72. Common Interview Question: What Happens When the Model Is Updated?

Answer:

> "I would treat the model as a versioned artifact. A new model would first be trained and evaluated, then validated against the existing production model. Only after meeting the acceptance criteria would it replace the production version. The API should then load the approved model version."

# 73. Common Interview Question: How Would You Monitor the API?

Answer:

> "I would monitor both application-level and model-level metrics. At the API level I would track request count, latency, error rate and throughput. At the model level I would track prediction distributions, risk-band proportions and, once actual outcomes are available, precision, recall, F1 and ROC-AUC. I would also monitor data drift."

# 74. Common Interview Question: How Would You Scale It?

Answer:

> "For real-time inference I would run multiple API instances behind a load balancer and load the model once per instance. Since individual tabular predictions are independent, horizontal scaling is straightforward. For large workloads, I would use batch inference rather than sending one request per customer."

# 75. Common Interview Question: What Would You Do If Prediction Latency Increased?

Answer:

> "First I would measure where the latency is coming from: request validation, preprocessing, model inference or infrastructure. I would check application metrics and logs, profile the prediction path if necessary, and then optimize the actual bottleneck. I would avoid assuming that the model itself is the problem."

# 76. Common Interview Question: How Would You Secure the API?

# 77. Common Interview Question: What is the Difference Between Model Deployment and Model Retraining?

Answer:

> "Deployment makes an existing trained model available for inference. Retraining creates a new model from updated data. Retraining is an ML lifecycle process, while deployment is the process of serving an approved model to consumers."

# 78. Common Interview Question: What Happens If the API Receives Invalid Data?

Answer:

> "The API validation layer should reject structurally invalid data before it reaches the model. For values that require domain-level validation, I would add explicit constraints. The API should return a controlled client error rather than allowing invalid data to produce an unreliable prediction."
